C1

Student Service Code — Controller, Service & Kafka Producer

This is the simplest service. It follows the pattern: Controller → Service → Database + Kafka Producer. Let's understand each file.

1. Student Entity (Student.java)

This is the database table definition. @Entity tells Spring to create a table called students.

Student.java @Entity @Table(name = "students") public class Student { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; // auto-generated primary key private String name; // student name private String email; // student email private String phone; // student phone private LocalDateTime createdAt; // when created }

2. Student Controller (StudentController.java)

This is the REST API entry point. When Postman sends a request to /api/students, this class handles it.

StudentController.java @RestController // This class handles HTTP requests @RequestMapping("/api/students") // Base URL for all endpoints public class StudentController { private final StudentService studentService; // Injected by Spring // POST /api/students - Create a new student @PostMapping public ResponseEntity<Student> createStudent( @Valid @RequestBody StudentRequestDTO requestDTO) { // 1. Receives JSON body from Postman // 2. Calls studentService.createStudent() // 3. Returns created student with HTTP 201 Student created = studentService.createStudent(requestDTO); return ResponseEntity.status(HttpStatus.CREATED).body(created); } // GET /api/students - Get all students @GetMapping public List<Student> getAllStudents() { return studentService.getAllStudents(); } // GET /api/students/{id} - Get student by ID @GetMapping("/{id}") public Student getStudentById(@PathVariable Long id) { return studentService.getStudentById(id); } }

3. Student Service (StudentService.java) — The Business Logic

This is where the real work happens. It saves to database AND publishes to Kafka.

StudentService.java @Service public class StudentService { private final StudentRepository studentRepository; // Database access private final StudentEventProducer eventProducer; // Kafka producer public Student createStudent(StudentRequestDTO requestDTO) { // Step 1: Check if email already exists if (studentRepository.existsByEmail(requestDTO.getEmail())) { throw new RuntimeException("Student with email already exists"); } // Step 2: Save student to database Student student = new Student(name, email, phone); Student savedStudent = studentRepository.save(student); // Step 3: Publish event to Kafka (fire-and-forget, async) // This is the KEY LINE - after saving to DB, we tell Kafka // "Hey, a new student was created!" StudentEvent event = new StudentEvent( "STUDENT_CREATED", // event type savedStudent.getId(), // student ID savedStudent.getName(), // student name savedStudent.getEmail(), // student email savedStudent.getPhone() // student phone ); eventProducer.publishStudentCreated(event); // <<< SEND TO KAFKA return savedStudent; } }

4. Student Kafka Producer (StudentEventProducer.java)

This class sends the event to Kafka. It uses KafkaTemplate (provided by Spring Kafka).

StudentEventProducer.java @Component public class StudentEventProducer { private static final String TOPIC = "student-events"; // Kafka topic name private final KafkaTemplate<String, StudentEvent> kafkaTemplate; // Spring Kafka public void publishStudentCreated(StudentEvent event) { // kafkaTemplate.send(topicName, key, value) // - topic: "student-events" // - key: student ID (used for partitioning) // - value: the StudentEvent object (serialized to JSON) kafkaTemplate.send(TOPIC, String.valueOf(event.getStudentId()), event); } }
Flow Summary: Postman POST request → StudentController receives it → StudentService saves to DB → StudentEventProducer sends event to Kafka topic student-events → notification-service automatically receives this event because it is a consumer of this topic.

Enrollment Service Code — Saga Orchestrator

This is the most important service. It starts the Saga pattern — creates an enrollment, publishes to Kafka, and later receives the payment result.

1. Enrollment Controller (EnrollmentController.java)

EnrollmentController.java @RestController @RequestMapping("/api/enrollments") public class EnrollmentController { // POST /api/enrollments - This triggers the FULL SAGA @PostMapping public ResponseEntity<EnrollmentResponseDTO> createEnrollment( @Valid @RequestBody EnrollmentRequestDTO requestDTO) { // requestDTO contains: { studentId: 1, courseId: 1 } EnrollmentResponseDTO response = enrollmentService.createEnrollment(requestDTO); return ResponseEntity.status(HttpStatus.CREATED).body(response); } }

2. Enrollment Service (EnrollmentService.java) — The Saga Starter

This is where the whole saga begins. Pay attention to the 5 steps:

EnrollmentService.java - createEnrollment() @Service public class EnrollmentService { // URLs to call other services directly (sync REST calls) private static final String STUDENT_URL = "http://localhost:8081/api/students"; private static final String COURSE_URL = "http://localhost:8083/api/courses"; public EnrollmentResponseDTO createEnrollment(EnrollmentRequestDTO requestDTO) { // STEP 1: Verify student exists (sync REST call to student-service) StudentDTO student = restTemplate.getForObject( STUDENT_URL + "/" + requestDTO.getStudentId(), StudentDTO.class ); // STEP 2: Verify course exists (sync REST call to course-service) CourseDTO course = restTemplate.getForObject( COURSE_URL + "/" + requestDTO.getCourseId(), CourseDTO.class ); // STEP 3: Save enrollment with PENDING status Enrollment enrollment = new Enrollment(studentId, courseId); // Status starts as "PENDING" - will change to "CONFIRMED" later Enrollment saved = enrollmentRepository.save(enrollment); // STEP 4: Publish ENROLLMENT_CREATED event to Kafka // This is ASYNC - payment-service will pick this up later EnrollmentEvent event = new EnrollmentEvent( "ENROLLMENT_CREATED", saved.getId(), student.getId(), student.getName(), student.getEmail(), course.getId(), course.getName(), course.getPrice() ); eventProducer.publishEnrollmentCreated(event); // <<< TO KAFKA // STEP 5: Return response immediately (don't wait for payment) // Status is still "PENDING" at this point! return buildResponse(saved, student, course); } }
Important: Notice that createEnrollment() returns immediately with status "PENDING". It does NOT wait for payment. The payment happens asynchronously via Kafka. Later, the PaymentEventConsumer (below) will update the status to "CONFIRMED".

3. Enrollment Event Producer (EnrollmentEventProducer.java)

EnrollmentEventProducer.java @Component public class EnrollmentEventProducer { private static final String TOPIC = "enrollment-events"; public void publishEnrollmentCreated(EnrollmentEvent event) { // Send to Kafka topic "enrollment-events" // payment-service is listening to this topic! kafkaTemplate.send(TOPIC, String.valueOf(event.getEnrollmentId()), event); } }

4. Payment Event Consumer (PaymentEventConsumer.java) — Saga Completion

This is the other end of the saga. After payment-service processes the payment, it publishes a result event. This consumer picks it up and updates the enrollment status.

PaymentEventConsumer.java (in enrollment-service) @Component public class PaymentEventConsumer { // @KafkaListener = "I am listening to this Kafka topic" // topics = which topic to listen // groupId = consumer group (each group gets ALL messages) @KafkaListener(topics = "payment-events", groupId = "enrollment-group") public void handlePaymentEvent(PaymentEvent event) { // Find the enrollment and update its status enrollmentRepository.findById(event.getEnrollmentId()).ifPresent(enrollment -> { if ("PAYMENT_SUCCESS".equals(event.getEventType())) { enrollment.setStatus("CONFIRMED"); // PENDING -> CONFIRMED // SAGA COMPLETE! Enrollment is confirmed! } else if ("PAYMENT_FAILED".equals(event.getEventType())) { enrollment.setStatus("FAILED"); // PENDING -> FAILED // SAGA FAILED! Payment was declined } enrollmentRepository.save(enrollment); // Save updated status }); } }
The Saga Pattern explained in code:
1. EnrollmentService.createEnrollment() saves enrollment as PENDING and publishes to Kafka
2. PaymentService (in payment-service) picks up the event and processes payment
3. PaymentEventConsumer (above) picks up the payment result and updates PENDING → CONFIRMED

No service directly calls another for payment. Everything goes through Kafka events!

Payment Service Code — Event-Driven Consumer & Producer

Payment service is fully event-driven. It has NO REST endpoint to create payments. It only reacts to Kafka events.

1. Enrollment Event Consumer (EnrollmentEventConsumer.java)

This consumer listens to enrollment-events topic. When a student enrolls, this class automatically triggers payment processing.

EnrollmentEventConsumer.java (in payment-service) @Component public class EnrollmentEventConsumer { private final PaymentService paymentService; // Listen to enrollment-events topic // groupId = "payment-group" (separate from notification-group) @KafkaListener(topics = "enrollment-events", groupId = "payment-group") public void handleEnrollmentEvent(EnrollmentEvent event) { if ("ENROLLMENT_CREATED".equals(event.getEventType())) { // Delegate to PaymentService to process the payment paymentService.processPayment(event); } } } // KEY CONCEPT: enrollment-service doesn't know payment-service exists! // enrollment-service just publishes an event to Kafka. // payment-service independently listens and reacts. // This is LOOSE COUPLING via event-driven architecture.

2. Payment Service (PaymentService.java) — Simulated Payment Gateway

This simulates a real payment gateway (like Stripe/Razorpay). In production, you'd call the actual payment API here.

PaymentService.java @Service public class PaymentService { public void processPayment(EnrollmentEvent enrollmentEvent) { // Step 1: Create payment record in DB with PENDING status Payment payment = new Payment( enrollmentEvent.getEnrollmentId(), enrollmentEvent.getStudentId(), enrollmentEvent.getStudentName(), enrollmentEvent.getStudentEmail(), enrollmentEvent.getCourseId(), enrollmentEvent.getCourseName(), enrollmentEvent.getCoursePrice() // amount to charge ); Payment saved = paymentRepository.save(payment); // Step 2: Simulate payment processing (2 sec delay) // In real world: call Stripe/PayPal/Razorpay API here Thread.sleep(2000); // Step 3: 90% chance success, 10% chance failure boolean success = random.nextInt(10) < 9; if (success) { String transactionId = "TXN-" + UUID.randomUUID(); saved.setStatus("SUCCESS"); saved.setTransactionId(transactionId); paymentRepository.save(saved); // Publish PAYMENT_SUCCESS event to Kafka PaymentEvent event = new PaymentEvent("PAYMENT_SUCCESS", ...); eventProducer.publish(event); // <<< TO KAFKA } else { saved.setStatus("FAILED"); saved.setFailureReason("Payment gateway declined"); paymentRepository.save(saved); // Publish PAYMENT_FAILED event to Kafka PaymentEvent event = new PaymentEvent("PAYMENT_FAILED", ...); eventProducer.publish(event); // <<< TO KAFKA } } }

3. Payment Event Producer (PaymentEventProducer.java)

PaymentEventProducer.java @Component public class PaymentEventProducer { private static final String TOPIC = "payment-events"; public void publish(PaymentEvent event) { // Send payment result to Kafka // TWO services are listening to this topic: // 1. enrollment-service (updates PENDING -> CONFIRMED) // 2. notification-service (sends payment receipt email) kafkaTemplate.send(TOPIC, String.valueOf(event.getEnrollmentId()), event); } }
Payment Service Flow: Kafka delivers enrollment event → EnrollmentEventConsumer receives it → PaymentService processes payment (simulated) → PaymentEventProducer sends result back to Kafka → enrollment-service and notification-service both receive the result automatically.

Notification Service Code — Kafka Consumer & RabbitMQ Producer

This service is the bridge between Kafka and RabbitMQ. It listens to ALL Kafka topics, creates notification records, and dispatches email tasks to RabbitMQ.

1. Notification Event Consumer (NotificationEventConsumer.java)

This is the ONLY consumer that listens to ALL 4 Kafka topics.

NotificationEventConsumer.java @Component public class NotificationEventConsumer { private final NotificationService notificationService; // ===== LISTENS TO student-events ===== @KafkaListener(topics = "student-events", groupId = "notification-group") public void handleStudentEvent(StudentEvent event) { if ("STUDENT_CREATED".equals(event.getEventType())) { notificationService.createAndDispatch( "STUDENT_CREATED", event.getEmail(), // send email to this address "Welcome to the System!", // email subject "Hi " + event.getName() + ", your account is created.", event.getStudentId() ); } } // ===== LISTENS TO enrollment-events ===== @KafkaListener(topics = "enrollment-events", groupId = "notification-group") public void handleEnrollmentEvent(EnrollmentEvent event) { // Creates "Enrollment Pending" notification + email notificationService.createAndDispatch(...); } // ===== LISTENS TO payment-events ===== @KafkaListener(topics = "payment-events", groupId = "notification-group") public void handlePaymentEvent(PaymentEvent event) { if ("PAYMENT_SUCCESS".equals(event.getEventType())) { // Creates "Payment Successful" notification + email notificationService.createAndDispatch( "PAYMENT_SUCCESS", event.getStudentEmail(), "Payment Successful - " + event.getCourseName(), "Your payment of $" + event.getAmount() + " was successful!", event.getPaymentId() ); } } }

2. Notification Service (NotificationService.java) — Save + Dispatch

This method does TWO things: saves to database AND sends to RabbitMQ.

NotificationService.java @Service public class NotificationService { private final NotificationRepository notificationRepository; // DB private final EmailMessageProducer emailMessageProducer; // RabbitMQ public Notification createAndDispatch(String type, String recipient, String subject, String body, Long refId) { // Step 1: Save notification to database (audit trail) Notification notification = new Notification(type, "EMAIL", recipient, subject, body); Notification saved = notificationRepository.save(notification); // Step 2: Send email task to RabbitMQ (background processing) // This is INSTANT - does not wait for email to actually send EmailMessage emailMessage = new EmailMessage(recipient, subject, body, type, refId); emailMessageProducer.sendEmailTask(emailMessage); // <<< TO RABBITMQ return saved; } }

3. Email Message Producer (EmailMessageProducer.java) — RabbitMQ Producer

This sends the email task to RabbitMQ. Notice the difference from Kafka producer.

EmailMessageProducer.java @Component public class EmailMessageProducer { private final RabbitTemplate rabbitTemplate; // Spring AMQP (RabbitMQ) public void sendEmailTask(EmailMessage emailMessage) { rabbitTemplate.convertAndSend( RabbitMQConfig.EXCHANGE_NAME, // "notification.exchange" RabbitMQConfig.EMAIL_ROUTING_KEY, // "email.send" emailMessage // the message object ); } } // DIFFERENCE FROM KAFKA: // Kafka: kafkaTemplate.send(TOPIC, key, event) // - Publishes to a topic, MANY consumers can read // // RabbitMQ: rabbitTemplate.convertAndSend(exchange, routingKey, message) // - Sends to exchange -> routes to queue // - EXACTLY ONE consumer picks it up from the queue
Why both Kafka AND RabbitMQ here?
Kafka brings the event INTO notification-service (one event, many consumers).
RabbitMQ sends the email task OUT to email-worker-service (one task, one worker picks it up).
Different tools for different jobs!

Email Worker Service Code — RabbitMQ Consumer

This is the simplest service. It only consumes messages from RabbitMQ's email.queue and simulates sending emails.

Email Consumer (EmailConsumer.java)

EmailConsumer.java @Component public class EmailConsumer { // @RabbitListener = "I am listening to this RabbitMQ queue" // When a message arrives in "email.queue", this method runs @RabbitListener(queues = "email.queue") public void processEmail(EmailMessage message) { log.info("Picked up email task from queue"); log.info("To : {}", message.getTo()); log.info("Subject : {}", message.getSubject()); // Simulate email sending (1 second delay) // In production, use JavaMailSender, SendGrid, or AWS SES Thread.sleep(1000); log.info("====== EMAIL SENT ======"); log.info("To : {}", message.getTo()); log.info("Subject : {}", message.getSubject()); log.info("Body : {}", message.getBody()); log.info("Email delivered successfully!"); } } // RABBITMQ CONCEPTS IN THIS CLASS: // // 1. @RabbitListener: Spring auto-registers this as a consumer // 2. Auto-Acknowledgment: If method succeeds, message is ACK'd // If method throws exception, message is NACK'd and retried // 3. After 3 retries, message goes to email.dlq (Dead Letter Queue) // 4. Prefetch=1: Only takes one message at a time
@KafkaListener vs @RabbitListener:
@KafkaListener(topics = "payment-events") — Listens to a Kafka topic. Multiple consumer groups can ALL read the same messages.
@RabbitListener(queues = "email.queue") — Listens to a RabbitMQ queue. Only ONE consumer picks up each message (competing consumers pattern).

Student service receives the request as if the client called it directly!

Service Responsibilities — What Each Service Does

In this project, every service has its own responsibility. Each service is independent — it has its own database, its own code, and runs on its own port. This is the core idea of microservices architecture.

  • ➤
    student-service Handles student-related data. When you create, read, or update a student, this service does the work. Runs on port 8081.
  • ➤
    course-service Handles course-related data. Manages all CRUD operations for courses (create, read, update, delete). Runs on port 8083.
  • ➤
    enrollment-service Handles student-course enrollment. When a student enrolls in a course, this service creates the enrollment record and kicks off the entire saga flow. Runs on port 8084.
  • ➤
    payment-service Handles payment processing. It does NOT have a REST endpoint to create payments — it is purely event-driven. It listens for enrollment events via Kafka and auto-processes payment. Runs on port 8085.
  • ➤
    notification-service The notification hub. It listens to ALL Kafka topics (student, course, enrollment, payment events) and creates notification records. It also dispatches email tasks to RabbitMQ. Runs on port 8082.
  • ➤
    email-worker-service Sends emails asynchronously. It is a stateless background worker that picks up email tasks from RabbitMQ's email.queue and processes them. Runs on port 8086.
  • ➤
    api-gateway The single entry point for all client requests. Clients (Postman, frontend) only talk to the gateway on port 8080. The gateway routes requests to the correct service. Runs on port 8080.
Why so many services? We added multiple services to properly demonstrate how Kafka and RabbitMQ work together in a real microservices architecture. Each service has a clear boundary and communicates asynchronously with others.

Why Kafka? — Event-Driven Communication

We implemented Kafka for event-driven communication between services. Instead of one service directly calling another (tight coupling), services communicate by producing and consuming events.

How It Works (Simple Explanation)

When something important happens in a service, it produces an event to a Kafka topic. Other services that care about this event are consumers of that topic — they automatically receive the event.

EXAMPLE: Payment is successful payment-service (PRODUCER) | | publishes event: "Payment completed for enrollment #1" v ============================================= KAFKA TOPIC: payment-events ============================================= | | | v v v notification enrollment (any future -service -service service) (CONSUMER) (CONSUMER) (CONSUMER) ALL connected services get notified automatically!

Real Example from This Project

Role Service What It Does
Producer payment-service When payment is successful, it publishes a PAYMENT_SUCCESS event to Kafka
Consumer notification-service Receives the event and creates a notification + sends email task
Consumer enrollment-service Receives the event and updates enrollment status from PENDING to CONFIRMED
Key Benefit: If payment is successful, ALL connected services get notified automatically. The payment-service doesn't need to know about notification-service or enrollment-service. It just publishes the event, and whoever is listening will receive it. This is called loose coupling.

All Kafka Topics in This Project

Kafka Topic Producer Consumers Triggered When
student-events student-service notification-service A new student is created
course-events course-service notification-service A new course is created
enrollment-events enrollment-service payment-service, notification-service A student enrolls in a course
payment-events payment-service enrollment-service, notification-service Payment is processed (success/fail)

Why RabbitMQ? — Background Task Processing

We implemented RabbitMQ for background tasks and reliable queue processing. Some tasks (like sending emails) are slow and should not block the main API response.

How It Works (Simple Explanation)

WITHOUT RabbitMQ (BAD): ======================== Client sends request | v notification-service receives Kafka event | v notification-service tries to SEND EMAIL (slow! 2-3 seconds) | v Client is STILL WAITING... (blocked!) WITH RabbitMQ (GOOD): ======================== Client sends request | v notification-service receives Kafka event | v notification-service puts email task in RabbitMQ queue (instant!) | v Response sent back immediately (fast!) ... meanwhile, in the background ... email-worker-service picks up the task from queue | v Email is sent (nobody is waiting!)

Real Example from This Project

1. notification-service receives a Kafka event (e.g., payment completed)
2. It creates a notification record in its database
3. It sends an email message to RABBITMQ   email.queue (this is instant)
4. email-worker-service picks up the message from the queue in the background
5. Email is sent asynchronously — nobody is blocked!
Key Benefit: Email sending should NOT block the main API response. RabbitMQ acts as a buffer — tasks are queued and processed in the background. If email-worker-service is temporarily down, messages stay safe in the queue and are processed when the worker comes back up. This is called reliable message processing.

What Happens If Email Sending Fails?

Attempt Wait Time What Happens
1st try Immediate Email worker tries to send the email
2nd try 1 second First retry with backoff
3rd try 2 seconds Second retry with exponential backoff
After 3 fails — Message goes to email.dlq (Dead Letter Queue) for manual inspection

Kafka vs RabbitMQ — When to Use Which

Both Kafka and RabbitMQ are message brokers, but they serve different purposes. In this project, we use both because they solve different problems.

KAFKA   Event Streaming

  • Event streaming between services
  • Communication between multiple services
  • Broadcasting events to many consumers
  • One event, many listeners
  • Events are persisted (can replay)
  • High throughput, real-time

RABBITMQ   Task Queue

  • Task queues for background jobs
  • Reliable message processing
  • Retry mechanisms with dead letter
  • One task, one worker picks it up
  • Message deleted after processing
  • Great for slow/unreliable tasks

In This Project

Scenario Broker Used Why
Student created → notify multiple services KAFKA Multiple services need to know about the event
Enrollment created → trigger payment KAFKA Event-driven communication between services
Payment completed → update enrollment + notify KAFKA Broadcasting to enrollment-service AND notification-service
Send email in background RABBITMQ Slow task, needs retry mechanism, should not block API
Simple Rule of Thumb: Use Kafka when you want to say "Hey everyone, this happened!" (event broadcasting).
Use RabbitMQ when you want to say "Hey worker, do this task for me in the background" (task delegation).

API Gateway — How It Works & Why We Need It

What is the API Gateway?

The API Gateway is the single entry point for all client requests. Instead of clients (Postman, frontend app, mobile app) calling each microservice directly on different ports, they only call the gateway on port 8080. The gateway then routes the request to the correct service.

Why Do We Need It?

WITHOUT API Gateway (Bad)

Client must know every service port:

http://localhost:8081/api/students
http://localhost:8082/api/notifications
http://localhost:8083/api/courses
http://localhost:8084/api/enrollments
http://localhost:8085/api/payments
http://localhost:8086/api/email-worker

6 different URLs to remember!

WITH API Gateway (Good)

Client only knows ONE address:

http://localhost:8080/api/students
http://localhost:8080/api/notifications
http://localhost:8080/api/courses
http://localhost:8080/api/enrollments
http://localhost:8080/api/payments
http://localhost:8080/api/email-worker

1 single URL for everything!

How Does Routing Work?

The gateway reads the URL path and decides which service to forward the request to:

/api/students/** → localhost:8081 (student-service)
/api/courses/** → localhost:8083 (course-service)
/api/enrollments/** → localhost:8084 (enrollment-service)
/api/payments/** → localhost:8085 (payment-service)
/api/notifications/** → localhost:8082 (notification-service)
/api/email-worker/** → localhost:8086 (email-worker-service)

Visual Flow

Client (Postman / Browser / Mobile App) | | POST http://localhost:8080/api/students | v +---------------------+ | API GATEWAY | Port 8080 | (Spring Cloud) | | | | Reads the URL path: | | "/api/students/**" | | | | Finds matching | | route config | | | | Forwards to: | | localhost:8081 | +----------+-----------+ | v +----------+-----------+ | STUDENT SERVICE | Port 8081 | | | Receives the request | | as if client called | | it directly | +----------------------+

Benefits of API Gateway

Benefit Explanation
Single Entry Point Client only needs to know one URL (localhost:8080). No need to remember 6 different ports.
Hide Internal Architecture Client doesn't know (or care) how many services exist behind the gateway. Services can be added, removed, or moved to different ports without client changes.
Centralized Cross-Cutting Concerns In the future, you can add authentication, rate limiting, CORS, logging, etc. at the gateway level — once for ALL services.
Load Balancing (future) If you run multiple instances of student-service, the gateway can distribute requests between them.
Security Only the gateway is exposed to the internet. Internal services can be hidden behind a firewall.

Configuration (application.yml)

The gateway uses Spring Cloud Gateway. The routing is configured in api-gateway/src/main/resources/application.yml:

application.yml spring: cloud: gateway: routes: - id: student-service uri: http://localhost:8081 predicates: - Path=/api/students/** - id: course-service uri: http://localhost:8083 predicates: - Path=/api/courses/** - id: enrollment-service uri: http://localhost:8084 predicates: - Path=/api/enrollments/** # ... and so on for each service
How to read this config: "If a request comes with path /api/students/**, forward it to http://localhost:8081." That's it! The ** means any sub-path matches too (e.g., /api/students/1, /api/students/search?name=John).

RabbitMQ Queues & Email Flow

RabbitMQ Topology

notification.exchange (Topic Exchange) | |--- routing key: "email.send" ---> email.queue | | | |-- (on failure after 3 retries) | | | v | email.dlq (Dead Letter Queue) | +--- [future] "sms.send" ----------> sms.queue

RabbitMQ Components

Component Name Purpose
Exchange notification.exchange Routes messages to queues by routing key
Queue email.queue Holds email tasks for email-worker to process
Dead Letter Queue email.dlq Stores failed messages after 3 retry attempts
Routing Key email.send Binds exchange to email.queue

Troubleshooting Common Issues

Problem Cause Solution
Enrollment stays PENDING Kafka not delivering events Check Kafka & Zookeeper: docker-compose ps
No payment record created Payment service not consuming Check payment-service terminal for errors
No notifications in DB Notification service not consuming Check notification-service terminal
No email worker activity RabbitMQ not running Check container + visit http://localhost:15672
Connection refused on :8080 API Gateway not running Start api-gateway service first
404 on endpoints Target service not running Ensure the service is running on its port
Messages in email.dlq Email worker failing Check email-worker-service logs
"Broker not available" Kafka not started docker-compose up -d and wait 30s

Recommended Startup Order

1. Docker Compose — Start Kafka, Zookeeper, RabbitMQ: docker-compose up -d
2. Wait 30 seconds — Let Kafka fully initialize
3. API Gateway — Start first (port 8080)
4. Student & Course Service — Start next (ports 8081, 8083)
5. Enrollment, Payment, Notification, Email Worker — Start last
